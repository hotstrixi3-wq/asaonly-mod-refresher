> działał dla map zainstalowanych przez SteamCMD managera („Access Denied” dla
> manifestu starego buildu; 25.09.2026: 9 restartów bez aktualizacji). Aktualny
> opis: `V3.86-AKTUALIZACJA-SERWERA-PRZEZ-CACHE.md`.

Nowy plugin **88 „Aktualizacja serwera (SteamCMD)”** (przycisk **UPDATE SERWERA**):
sam sprawdza na Steamie najnowszy build serwera ASA i aktualizuje każdą mapę
bez udziału człowieka. Refresher nadal **nie uruchamia serwerów** — robi to
manager, jak po każdym DoExit.

## 3.85.1 — PIERWSZE URUCHOMIENIE NA WINDOWS I POPRAWKA
Na komputerze serwerów (25.09, rano) V3.85 zrobiła to, co miała:
- 05:29:57 pobrała SteamCMD od Valve do `C:\AAA\V3.85 …\STEAMCMD\` (ścieżka ze
  spacjami i nawiasami działa),
- 05:30:16: `[SERWER] Steam: build 25489097 (manifest 8699400601246504390, źródło:
  SteamCMD)` — wydruk konsoli SteamCMD czytelny, zapas z `appinfo.vdf` niepotrzebny;
  to ten sam manifest, który 24.09 o 22:56:46 widziało API w managerze,
- diagnostyka: „SteamCMD: jest; manager: dostępny” — refresher ma dostęp do
  wstrzymania procesu managera,
- wszystkie trzy mapy miały już build 25489097, więc plugin słusznie nic nie robił.
  Z logów managera: mapy zaktualizowano w nocy ręcznie — zatrzymanie (00:40–00:43),
  „Server file validation completed” (00:44 Genesis, 00:46 Ragnarok, 00:48 Extinction),
  start (00:53–00:56). Wcześniej, o 23:57:56, metoda aktualizacji managera została
  zmieniona na SteamCMD — i ta od razu pokazała „Update needed: True”, a o 00:19
  pobrała nowy build do `ASA UPDATES` („Servers not updated (automatic server updates
  disabled)”). Czyli nowego buildu nie widziała metoda CDN managera.

Znaleziony błąd (poprawiony w 3.85.1): host pluginów dla pluginu z `prepare()` woła
`activate()`, nie `start()`. Plugin 88 nie miał `activate()`, więc przy starcie
programu nie odzyskiwał managera wstrzymanego przez poprzednie uruchomienie,
a pierwsze sprawdzenie Steama szło od razu (w logu: pobieranie SteamCMD w chwili
startu), zamiast po minucie. Przy okazji: zmiana języka w trakcie instalacji
podmieniała zamrażarkę — po instalacji manager zostałby wstrzymany. Teraz:
`activate()` robi odzyskanie i planuje pierwsze sprawdzenie; `prepare()` nie
podmienia aktywnej zamrażarki; odzyskanie nie rusza dzierżawy żywego refreshera
(np. tego samego procesu po zmianie języka). Testy na prawdziwym hoście pluginów
(start programu, zmiana języka) nie przechodziły na V3.85, przechodzą na 3.85.1.

Nadal nie sprawdzone na Windows: sama instalacja (wstrzymanie managera → SteamCMD
`app_update` → wznowienie) — ruszy przy następnym buildzie serwera ASA.

## JAK DZIAŁA
1. **Co 20 min** (pierwszy raz minutę po starcie programu) plugin pyta Steama
   własnym SteamCMD: `+login anonymous +app_info_update 1 +app_info_print 2430930`
   (×4, jak WindowsGSM), po usunięciu `appcache\appinfo.vdf` — stary cache potrafi
   podać stary build (LinuxGSM usuwa go z tego powodu). Build =
   `depots → branches → public → buildid`. Gdy wydruk w konsoli jest ucięty
   (znany problem SteamCMD na Windows przy przekierowanym wyjściu), build jest
   czytany z binarnego `appinfo.vdf` — parser sprawdzony na prawdziwym pliku
   z SteamCMD managera.
2. **Build mapy** = `buildid` z jej `appmanifest_2430930.acf` (plus `StateFlags` 4 =
   w pełni zainstalowana). Katalog serwera wynika z folderu logu mapy:
   `…\ShooterGame\Saved\Logs` → katalog nad `ShooterGame`.
3. **Mapa GOTOWA ze starszym buildem** → zlecenie restartu w zwykłej kolejce:
   sprawdzenie graczy, ogłoszenia z harmonogramu RCON tej mapy (pusta = od razu),
   jeden start naraz.
4. **Tuż przed DoExit** plugin wstrzymuje proces managera (NtSuspendProcess
   z ntdll — cały proces naraz). Bez tego manager podniósłby serwer ok. 30 s po
   zniknięciu procesu (jego log: trzy sprawdzenia co 10 s, potem „automatic
   restart”) — w trakcie instalacji. Serwer zapisuje świat i się wyłącza; plugin
   czeka, aż żaden `ArkAscendedServer.exe` z katalogu tej mapy nie działa
   (do 5 min), potem SteamCMD:
   `+force_install_dir <katalog mapy> +login anonymous +app_info_update 1 +app_update 2430930 validate +quit`.
5. **Po SteamCMD** plugin sprawdza appmanifest: build ≥ docelowy i `StateFlags` 4
   = sukces. Zawsze (także po błędzie) wznawia managera, a manager podnosi serwer
   sam. Start z aktualizacją nie jest zapisywany jako czas startu mapy (nie psuje
   planowania kolejki).
6. **Mapa, której serwer nie działa** (OFFLINE / CRASH) albo **od 30 min nie jest
   GOTOWA** (np. pętla krachów po modzie, który wymaga nowego serwera): DoExit
   jest niemożliwy. Gdy nie działa żaden proces serwera z katalogu tej mapy,
   plugin aktualizuje ją bez kolejki — wstrzymany manager, instalacja,
   wznowienie. Gdy proces serwera działa (np. manager właśnie go podnosi),
   managera nie wstrzymuje — aktualizacja pójdzie kolejką, gdy mapa będzie
   GOTOWA. Jeśli manager zdąży podnieść serwer tuż przed wstrzymaniem, nic nie
   jest instalowane i nie liczy się to jako nieudana próba. W czasie aktualizacji
   bez DoExit kolejka restartów nie rusza (dziennik: „Kolejka restartów czeka —
   …”), bo DoExit innej mapy czekałby na wznowienie managera.

## BEZPIECZNIKI
- **Manager nie zostanie wstrzymany na stałe:**
  - plik dzierżawy `CONFIG_PROGRAM\zamrozenie_managera.json` (co wstrzymane: PID
    i czas startu procesu — PID użyty ponownie przez inny proces nie jest ruszany),
  - osobny strażnik (`python -m asaonly.zamrazanie …`): gdy refresher zniknie,
    wznawia managera — a jeśli SteamCMD jeszcze instaluje, najpierw czeka na jego koniec,
  - po ponownym uruchomieniu refresher wznawia managera, jeśli dzierżawa została,
  - limity: brak DoExit przez 5 min → wznowienie; SteamCMD dłużej niż 2 h →
    przerwany; strażnik wznawia managera najpóźniej po 2,5 h (+30 min, jeśli
    SteamCMD nadal pracuje — wtedy go kończy).
- Manager rusza dopiero, gdy **żaden proces naszego SteamCMD** już nie działa
  (SteamCMD po samoaktualizacji potrafi uruchomić się ponownie jako nowy proces).
- Warunki sprawdzane **przed ogłoszeniami**: manager działa i da się go wstrzymać.
  Inaczej żadnych ogłoszeń ani DoExit, tylko wpis „Aktualizacja czeka: …”.
- Najwyżej **3 nieudane próby** do tego samego buildu, co najmniej 30 min odstępu;
  potem tylko ręcznie (panel).
- **Wspólna instalacja** kilku map — pomijana (SteamCMD wymaga wyłączenia
  wszystkich tych map naraz, a kolejka restartuje po jednej).
- Katalog **bez appmanifest** (nie instalacja SteamCMD) — pomijany.
- **Plugin OFF** = czekające zlecenia odwołane; rozpoczęta instalacja kończy się
  i wznawia managera.
- **Automat RCON wyłączony** = nic nie rusza samo (tylko AKTUALIZUJ TERAZ).

## USTAWIENIA (panel UPDATE SERWERA)
- „Instaluj automatycznie” (domyślnie tak), „Weryfikuj pliki” (`validate`,
  domyślnie tak), „Sprawdzaj Steam co [min]” (20, najmniej 5), „Proces managera
  do wstrzymania” (`ASADedicatedManager.exe`), „SteamCMD” (puste = własny
  w `STEAMCMD\` obok programu, pobierany od Valve przy pierwszym użyciu:
  `https://steamcdn-a.akamaihd.net/client/installer/steamcmd.zip`).
- **SPRAWDŹ TERAZ** — sprawdza (i działa jak automat). **AKTUALIZUJ TERAZ** —
  świeże sprawdzenie i aktualizacja od razu, także przy wyłączonym
  „automatycznie”, wyłączonym automacie RCON i mimo limitu prób.
- Tabela map: build na dysku, stan, katalog serwera; ostatnie wyjście SteamCMD.

## WYMAGANIA I UWAGI
- **Refresher jako administrator** (wstrzymanie procesu managera). Bez tego:
  „brak dostępu do procesu managera (uruchom refresher jako administrator)”
  i nic się nie dzieje.
- **Manager musi działać** — to on podnosi serwer po instalacji.
- Tylko **Windows** (SteamCMD serwera ASA, wstrzymanie procesu przez API Windows).
- **W managerze nic nie zmieniać:** `AutoApplyUpdates = False` i wyłączone
  automatyczne aktualizacje SteamCMD w tabach zostają jak są — wtedy pliki
  serwera aktualizuje tylko ten plugin.
- Plik managera `local_version.txt` w katalogu mapy (`ark_2491590067154671259` —
  ta sama liczba, co „Local Manifest Value” w jego logu) zostaje bez zmian:
  refresher nie zmienia plików managera. Manager może więc dalej pisać w logu mapy
  „Update needed: True”; przy `AutoApplyUpdates = False` nic z tego nie wynika.
- Każda mapa ma własną instalację, więc SteamCMD pobiera aktualizację **osobno
  dla każdej mapy** (manager pobiera raz do `ASA UPDATES` i kopiuje).
- Przez czas instalacji jednej mapy manager jest wstrzymany w całości — nie
  pilnuje wtedy także pozostałych map.
